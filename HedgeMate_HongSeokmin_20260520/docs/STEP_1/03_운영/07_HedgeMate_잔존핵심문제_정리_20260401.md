# HedgeMate 잔존 핵심 문제 정리 (2026-04-01)

## 1. 문서 목적
본 문서는 현재 HedgeMate 코드, 운영 문서, 최신 실행 산출물을 기준으로
아직 남아 있는 핵심 문제를 정리한 문서이다.

분석 기준은 아래 3가지다.

- 사용자 문제 제기: `지금 hedgemate의 문제.txt`
- 현재 구현: `scripts/run_data_pipeline.py`, `scripts/serve_dashboard.py`, `web/`
- 실제 결과물: `docs/STEP_1/04_실행결과/`, `outputs/reports/`

이 문서의 목적은
“무엇이 이미 반영되었는가”보다
“왜 아직도 결과가 사용자가 기대한 맞춤형 헷지처럼 보이지 않는가”를
핵심 이슈 중심으로 설명하는 데 있다.

---

## 2. 요약 결론
현재 HedgeMate는 초기 문제 제기의 일부를 반영했다.

- 단순 최근 수익률 추종 로직은 상당 부분 완화되었다.
- 추천안 / 참고안 / 실패 구분, Gate 판정, KRW 기준 분석, 자산 민감도 저장은 구현되었다.

그러나 핵심은 아직 남아 있다.

> 현재 HedgeMate는 **입력 자산의 대표 리스크를 먼저 해석하고 그 반대 논리의 자산을 찾는 엔진**이라기보다,  
> **safe haven 성격이 강한 후보군을 먼저 압축한 뒤 그 안에서 가장 방어적인 조합을 고르는 엔진**에 더 가깝다.

즉,
“헷지 엔진”의 외형은 갖췄지만
“입력 맞춤형 리스크 해석 + 논리별 대표 헷지안 제시”까지는 아직 도달하지 못했다.

---

## 3. 핵심 문제 요약표

| 우선순위 | 핵심 문제 | 현재 상태 요약 |
|---|---|---|
| P0 | 입력 자산 맞춤형 후보 선별 부재 | 후보 선별이 입력 자산 이전에 전역 점수로 이루어짐 |
| P0 | 정적 hedge universe 의존 | 기본 모드가 `hedge-only`이며 정해진 방어 후보군에 크게 의존 |
| P0 | 시장 상태 / 시나리오 분석 부재 | 전쟁, 금리, 인플레이션, 지정학 등 현재 시장 해석 로직이 없음 |
| P1 | 핵심 리스크 노출 지표 활용 부족 | downside beta 등은 계산되지만 실제 판정식 반영은 제한적 |
| P1 | 논리별 대표안 구조 부재 | 최종 출력은 사실상 best single / best multi 1개씩 |
| P1 | 수익 훼손 통제 미흡 | 계획 문서의 수익 훼손 제한식이 Gate에 반영되지 않음 |
| P1 | 조합 비중 최적화 부재 | 다자산 조합 가중치가 균등분배 중심 |
| P2 | DQ WARN 반영 약함 | FAIL만 강하게 제외되고 WARN은 신뢰도 패널티가 약함 |

## 4. 핵심 문제 상세

## 4.1 입력 자산 맞춤형 후보 선별이 아니다

### 현 상태
현재 후보 prefilter는 입력 자산이나 포트폴리오를 보기 전에,
각 후보 자산 자체의 특성만으로 HES 유사 점수를 계산해 정렬한다.

### 코드 근거
- `build_candidate_prefilter_rows()`는 후보 자체의 `corr_sp500_60d_krw`, `cvar_95_1y_krw`, `avg_stress_ret_krw`, `sharpe_1y_krw_proxy`, `adv_60`로만 전역 랭킹을 계산한다.
- `choose_candidate_pool()`은 이 전역 랭킹 결과를 버킷별로 잘라 입력 평가 단계에 넘긴다.

즉,
입력 자산과 후보의 관계가 아니라
후보 자체의 “방어형 성격”이 먼저 높은 점수를 받는다.

### 결과 근거
최신 결과 문서들에서 서로 다른 입력에도 유사한 결과가 반복된다.

- 포트폴리오 최적: `SHY`, `GLD + SHY`
- `TSLA 100%` 최적: `GLD`, `GLD + SHY`
- `KO 100%` 최적: `GLD`, `GLD + SHY`
- `USO 100%` 최적: `GLD`, `GLD + TLT`

이는 입력별 리스크 해석 차이가 충분히 후보 선별 단계에 반영되지 않는다는 강한 신호다.

### 영향
- 추천 결과의 차별성이 약해진다.
- “왜 이 입력에도 또 금/국채인가?”라는 사용자 의문이 반복된다.
- 사용자가 원하는 “맞춤형 헷지”보다 “범용 방어자산 추천”처럼 보인다.

### 우선 개선 방향
- 후보 선별 점수에 입력 자산/포트폴리오와의 관계를 먼저 넣어야 한다.
- 최소한 아래 축은 prefilter 단계로 끌어올리는 것이 필요하다.
  - downside correlation
  - downside beta / tail beta
  - drawdown 동행성
  - stress 구간 상대방어력

## 4.2 후보 유니버스가 여전히 정적이다

### 현 상태
기본 후보 모드는 `hedge-only`이며,
`is_core_hedge` 또는 하드코딩된 `HEDGE_V1_CANDIDATES`에 크게 의존한다.

즉,
현재 엔진은 “전체 유니버스에서 현 상황에 맞는 반대 논리 자산을 찾는다”기보다,
미리 정한 방어 후보 집합 안에서 답을 고르는 구조다.

### 코드 근거
- `HEDGE_V1_CANDIDATES`
- `is_hedge_candidate()`
- CLI에는 `--candidate-mode all`이 있지만 기본값은 `hedge-only`
- 현재 웹 UI에는 `candidate-mode` 선택이 노출되지 않는다

### 영향
- 사용자 문제 제기인
  “A 섹터가 오르면 B 섹터가 내리는 관계를 찾아 리스크를 줄인다”
  는 방향과 구조적으로 거리가 있다.
- 전쟁, 지정학, 경기둔화, 금리상승처럼
  특정 국면에서 실제 반대로 움직일 수 있는 자산을 동적으로 발굴하기 어렵다.

### 우선 개선 방향
- `hedge-only`는 운영 안전장치로 남기더라도,
  분석 단계에서는 `all` 기반 탐색이 가능해야 한다.
- UI/API에서도 후보 탐색 범위를 선택할 수 있게 해야 한다.
- 유니버스 메타데이터를 활용한 섹터/논리별 후보 탐색이 필요하다.

## 4.3 현재 시장 상태를 해석하는 엔진이 없다

### 현 상태
현재 “시장 상태”에 해당하는 것은 사실상 stress 구간 탐지뿐이다.
이 stress도 `SPY` 또는 `KS200`가 20거래일 동안 -8% 이하 하락한 경우만 감지한다.

즉,
시장분석은 아직 “위기구간 표시” 수준이고,
사용자 문제 제기에서 말한
“전쟁이면 방산, 지정학 리스크면 특정 자산 하락”
같은 시나리오 분류는 없다.

### 코드 근거
- `build_stress_dates()`는 `SPY + KS200` 가격 하락만 기준으로 stress 날짜를 만든다.
- 자산 민감도 요약 문서도 “직접 매크로 시계열/시나리오 확장은 차기 단계”라고 명시한다.
- `structural_tags`의 `geopolitical_proxy`, `inflation_proxy`, `defensive_proxy`는 현재 시장을 분석한 결과가 아니라 자산 메타 기반 정적 태그다.

### 영향
- 추천 설명이 “현재 장세에 왜 이 자산이 유리한가”까지 올라가지 못한다.
- 사용자는 결과를 보고도 시장 맥락과 연결된 설명을 얻기 어렵다.
- 프로젝트의 차별점이 약해진다.

### 우선 개선 방향
- 최소 MVP 수준의 regime 분류가 필요하다.
- 예시:
  - 금리상승 국면
  - 인플레이션 국면
  - 지정학 리스크 국면
  - 경기둔화 / 성장주 약세 국면
  - KRW 약세 국면
- 그 뒤 자산별 민감도를 “현재 regime에 대한 예상 반응”으로 연결해야 한다.

---

## 4.4 계산하는 지표와 실제 추천식 사이에 간극이 있다

### 현 상태
현재 엔진은 여러 지표를 계산한다.

- beta
- downside beta
- S&P500 60d correlation
- KOSPI200 60d correlation
- stress 평균 수익률

하지만 실제 Gate와 final score는
대체로 `CVaR / MDD / Stress / SPY beta·corr / 유동성` 중심이다.

즉,
계산은 하지만 추천식에 충분히 반영되지 않는 지표가 있다.

### 코드 근거
- `downside_beta_sp500_1y_krw`는 계산 및 저장되지만 Gate 기준에는 직접 들어가지 않는다.
- `corr_kospi200_60d_krw` 역시 민감도 저장에는 쓰이지만 추천 판정의 핵심축은 아니다.
- `benchmark_group` 메타 필드는 실제 추천 로직에서 사실상 활용되지 않는다.

### 영향
- 한국 자산, 특정 섹터, 특정 리스크의 특성이 충분히 살아나지 않는다.
- 추천이 결국 `SPY` 축 중심으로 단순화된다.
- 사용자가 기대하는 “왜 이 자산과 반대로 움직이는가” 설명이 빈약해진다.

### 우선 개선 방향
- Gate와 prefilter에 아래 지표를 단계적으로 반영해야 한다.
  - downside beta
  - downside correlation
  - drawdown 동행성
  - KOSPI200 기준 노출 변화
  - 입력 자산 benchmark group 맞춤 노출 축

## 4.5 논리별 대표안이 아니라 최고점 1개만 뽑는다

### 현 상태
계획 문서에서는 “논리별 대표안”을 뽑는 구조를 지향했지만,
현재 구현은 `best_single`, `best_multi`를 1개씩 고르는 방식이다.

즉,
현재는
“금 논리 대표안 1개, 금리 논리 대표안 1개, 방어섹터 논리 대표안 1개”
가 아니라
“전체 후보 중 점수 높은 것 1개”
에 가깝다.

### 코드 근거
- `best_single = max(...)`
- `best_multi = max(...)`

### 영향
- 결과 해석이 단선적이다.
- 사용자에게 선택지를 제공하더라도 “논리적으로 다른 대안”이 아니라 “점수 차이만 있는 유사안”처럼 보이기 쉽다.
- 설명 가능성이 약해진다.

### 우선 개선 방향
- 버킷 수준이 아니라 “헷지 논리” 수준으로 대표안을 뽑아야 한다.
- 예시:
  - 금리 민감 리스크 대응 대표안
  - 지정학 리스크 대응 대표안
  - 경기둔화 리스크 대응 대표안
  - KRW 약세 대응 대표안

---

## 4.6 수익 훼손 제한이 Gate에 반영되지 않았다

### 현 상태
개선 계획 문서에는 아래 제한이 명시되어 있다.

- `Sharpe_improve_pct >= -5`
- `연환산 기대수익 저하폭 <= 15%p`

하지만 현재 구현에서는 이 기준이 Gate에 직접 반영되지 않는다.
Sharpe는 final score의 일부일 뿐이고,
연환산 기대수익 저하 제한은 별도 Gate로 없다.

### 코드 근거
- `evaluate_gate()`는 `CVaR / MDD / Stress / exposure / liquidity`만 본다.
- `annual_return_krw`는 계산되지만 추천 통과 제한식에는 쓰이지 않는다.

### 영향
- 방어력은 좋아도 수익 훼손이 큰 조합이 PASS될 수 있다.
- safe haven 편향이 다시 강화된다.
- 프로젝트 철학인 “손실 완화 + 수익 훼손 최소화”가 완성되지 않는다.

### 우선 개선 방향
- Sharpe 또는 연환산 기대수익 훼손 제한을 Gate에 직접 추가해야 한다.
- 최소한 “극단적 방어형이지만 수익을 지나치게 죽이는 조합”은 추천안에서 제외해야 한다.

---

## 4.7 조합 비중이 균등분배 중심이라 맞춤형 최적화가 약하다

### 현 상태
현재 다자산 조합은 헷지 예산을 조합 내 자산 수만큼 균등 배분한다.
KRW 예산 모드도 `allocated_per_asset = hedge_budget_krw / len(combo)` 구조다.

즉,
조합은 고르지만
조합 내 가중치를 “입력 리스크를 가장 잘 줄이도록” 최적화하지는 않는다.

### 영향
- 같은 조합이라도 더 나은 비중 조합을 놓칠 수 있다.
- 입력별 맞춤형 추천 강도가 약해진다.
- 특정 자산이 핵심 hedge이고 나머지가 보조 hedge인 구조를 반영하기 어렵다.

### 우선 개선 방향
- 다음 단계에서는 조합 선택과 비중 선택을 분리해야 한다.
- 예시:
  - 간단한 grid search
  - 버킷별 최소/최대 비중 제약
  - CVaR / MDD / exposure 개선을 목표로 한 weight optimization

---

## 4.8 DQ WARN 비중이 높지만 점수상 신뢰도 패널티는 약하다

### 현 상태
최신 실행 결과 기준 DQ는 아래와 같다.

- PASS: 5
- WARN: 65
- FAIL: 0

현재 로직은 `FAIL`은 강하게 제외하지만,
`WARN`은 사실상 계산 허용 상태로 많이 통과한다.

### 영향
- 결과는 계산되지만 신뢰도 차이가 충분히 사용자에게 반영되지 않을 수 있다.
- 추천점수가 높아도 데이터 품질 불안정 자산이 상위에 남을 수 있다.

### 우선 개선 방향
- `WARN`에도 단계적 패널티가 필요하다.
- 예시:
  - coverage 낮음 패널티
  - FX carry-forward 잦음 패널티
  - 관측치 부족 패널티
  - 설명 문구에 신뢰도 수준 명시

## 5. 이번 문제 제기와의 대응 관계

| 사용자 문제 제기 | 반영 여부 | 현재 평가 |
|---|---|---|
| 최근 수익률 높은 자산만 고르는 것 같다 | 일부 반영 | 직접 수익률 추종은 줄었지만 safe haven 편향은 남아 있음 |
| 서로 반대로 움직이는 자산을 찾아야 한다 | 일부 반영 | beta/corr 일부 반영은 있으나 입력 맞춤형 관계 분석은 부족 |
| 리스크 차이를 통해 적절 수익률을 보장해야 한다 | 미완료 | 방어력은 보지만 수익 훼손 제한은 약함 |
| 현 시장을 분석해 어떤 자산이 오르고 내릴지 분류해야 한다 | 미반영에 가까움 | 정적 태그는 있으나 regime 분석 엔진은 없음 |
| 전쟁/지정학/섹터 관계를 반영해야 한다 | 미반영에 가까움 | 실제 추천 로직은 아직 해당 시나리오를 동적으로 해석하지 않음 |

## 6. 가장 먼저 고쳐야 할 우선순위

### 1순위
입력 자산 맞춤형 후보 선별로 전환

현재 문제의 대부분은 여기서 시작된다.
prefilter가 바뀌지 않으면,
뒤의 score/Gate를 조금씩 조정해도
결국 금·국채 중심 결과가 반복될 가능성이 높다.

### 2순위
시장 상태 / 리스크 시나리오 분류 추가

사용자 문제 제기의 핵심 차별점은
“지금 장세에서 어떤 자산이 방어적인가”이다.
이 축이 없으면 프로젝트 설명력이 약하다.

### 3순위
수익 훼손 제한 + 논리별 대표안 구조 도입

이 단계가 들어와야
결과가 “무조건 방어형”에서
“설명 가능한 맞춤형 헷지안”으로 바뀐다.

## 7. 최종 한 줄 판단

> HedgeMate는 현재 **KRW 기준 방어형 추천 엔진 v1**으로는 의미가 있지만,  
> 사용자가 기대한 **입력 맞춤형 리스크 해석 + 시장 시나리오 기반 헷지 추천 엔진**으로 보기에는 아직 핵심 구조가 부족하다.
