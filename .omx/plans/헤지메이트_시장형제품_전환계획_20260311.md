# 헤지메이트 시장형 제품 전환 계획 (2026-03-11)

## 1. 목적
현재 HedgeMate는 **분석 엔진 + 수동 실행형 대시보드** 단계까지 구현되어 있다.  
이 계획의 목적은 현재 저장소를 기반으로 HedgeMate를 **“시장에 통할 제품형 MVP”**로 전환하는 것이다.

이 계획에서 말하는 시장형 제품은 아래를 만족하는 상태를 의미한다.

- 사용자가 **입력 → 분석 → 결과 해석**까지 스스로 완료할 수 있다.
- 결과가 단순 수치표가 아니라 **추천안 / 참고안 / 신뢰도** 구조로 이해 가능하다.
- 핵심 시나리오가 재현 가능하고 데모/배포/설명이 가능하다.
- 현재 코드/문서/테스트 자산을 재사용하며 과도한 재설계는 하지 않는다.

---

## 2. 현재 기준선 (repo evidence)
- 분석 엔진: `scripts/run_data_pipeline.py`
- 웹 대시보드: `scripts/serve_dashboard.py`, `web/`
- 자동 테스트: `tests/test_run_data_pipeline.py`, `tests/test_dashboard_server.py`
- 운영/데이터 문서: `docs/STEP_1/...`
- 구조 문서: `엔진내부구조.md`
- 판정 문서: `추천판정기준.md`

즉, 현재는 **핵심 계산 로직과 기본 UI는 존재**하지만,  
제품 수준에서는 아직 다음이 부족하다.

- 사용자 관점의 핵심 가치 제안 정리
- 결과 해석 UX 고도화
- 신뢰도/경고의 일관된 노출
- 온보딩/데모/운영 패키징

---

## 3. 계획 가정
- 1차 출시 대상은 **한국 개인투자자 관점의 self-serve MVP**로 둔다.
- 기준통화는 계속 **KRW**를 유지한다.
- 예산 입력은 **KRW 우선** 정책을 유지한다.
- 추천안 / 참고안 구분은 현재 `추천판정기준.md`를 기준으로 유지한다.
- Top N 노출 정책은 핵심 제품 구조보다 후순위로 두고, 본 계획에서는 **출력 정책 보조 항목**으로만 다룬다.

---

## 4. 실행 계획

## Step 1. 제품 계약(Product Contract) 고정
### 목표
현재 “분석 툴”을 “누구를 위한 어떤 제품인지”로 번역한다.

### 작업
- 하나의 1차 사용자 시나리오를 고정한다.
  - 예: “한국 개인투자자가 보유 종목/포트폴리오의 방어 조합을 KRW 기준으로 확인”
- 핵심 사용자 흐름을 2개로 제한한다.
  1. 단일 종목 방어 분석
  2. 포트폴리오 방어 분석
- 결과의 공식 구조를 고정한다.
  - 추천안
  - 참고안
  - 리스크 개선 수치
  - 신뢰도/경고

### Acceptance Criteria
- 제품 설명 한 문장과 핵심 사용자 1종이 문서로 고정된다.
- 엔진/대시보드/문서가 모두 같은 핵심 흐름 2개를 중심으로 설명된다.
- “수익 추천기”가 아니라 “방어형 헷지 추천기”라는 포지셔닝이 문서와 UI에서 일관된다.

---

## Step 2. 사용자 입력 경험을 제품 수준으로 정리
### 목표
입력 진입장벽을 낮추고, 사용자가 스스로 분석을 시작할 수 있게 만든다.

### 작업
- 검색 UX를 “자동 선택”이 아니라 “후보를 보여주고 사용자가 정확한 자산을 선택”하는 흐름으로 정리한다.
- 포트폴리오 입력을 현실적인 제약으로 유지한다.
  - 합계 100%
  - 음수 금지
  - 개별 종목 50% 이하
- KRW 예산 입력을 기본값으로 유지하고, UI 설명 문구를 사용 목적 중심으로 정리한다.
- 샘플 입력/예시 포트폴리오를 제품 온보딩 자산으로 활용한다.

### Acceptance Criteria
- 신규 사용자가 별도 문서 없이 단일 종목 분석을 1회 실행할 수 있다.
- 신규 사용자가 샘플 또는 직접 입력으로 포트폴리오 분석을 1회 실행할 수 있다.
- 잘못된 입력 시 에러 문구가 “무엇을 고쳐야 하는지” 수준으로 설명된다.

---

## Step 3. 결과 화면을 “분석표”에서 “의사결정 화면”으로 전환
### 목표
숫자 나열이 아니라, 사용자 판단을 도와주는 결과 화면으로 바꾼다.

### 작업
- 결과 화면의 1차 정보 우선순위를 고정한다.
  1. 추천안 또는 참고안 여부
  2. 기존 대비 개선 정도
  3. 추천 이유
  4. 데이터 신뢰도/경고
- 단일 종목/포트폴리오 결과 화면의 구성 순서를 통일한다.
- 추천안이 없을 때는 참고안을 전면에 노출하되, **정식 추천이 아님**을 분명히 표시한다.
- 데이터 부족/경고 상태를 UI와 리포트에서 같은 의미로 노출한다.

### Acceptance Criteria
- 사용자가 결과 화면을 보고 “무엇이 추천인지 / 참고안인지 / 왜 그런지”를 바로 구분할 수 있다.
- 단일 종목과 포트폴리오 화면이 같은 정보 구조를 따른다.
- 추천안 0건 상황에서도 화면이 비지 않고, 참고안과 경고가 함께 노출된다.

---

## Step 4. 신뢰도와 재현성을 제품 기능으로 승격
### 목표
계산 엔진의 강점을 제품 신뢰 요소로 전환한다.

### 작업
- DQ, metric validation, 가용 구간 계산 정책을 사용자-facing 신뢰도 설명으로 연결한다.
- 결과 CSV/리포트/웹 화면의 핵심 용어를 통일한다.
- 대표 시나리오 3개를 고정해 회귀 검증 자산으로 사용한다.
  1. 단일 미국 주식
  2. 혼합 포트폴리오
  3. 추천안 0건 → 참고안 상황
- “재현 가능한 데모” 기준으로 실행 문서와 샘플 아티팩트를 정리한다.

### Acceptance Criteria
- 대표 시나리오 3개가 문서 + 테스트 + 결과 화면에서 재현 가능하다.
- 신뢰도 관련 용어가 문서/리포트/UI에서 일관된다.
- 사용자가 결과를 볼 때 “이 값이 얼마나 믿을 만한가”를 판단할 단서가 존재한다.

---

## Step 5. 출시 가능한 MVP 패키지로 마감
### 목표
현재 프로젝트를 설명 가능한 데모/배포형 MVP 패키지로 정리한다.

### 작업
- 실행 시작점(README 또는 제품 소개 문서)을 사용자 중심으로 재정리한다.
- “처음 보는 사람이 5분 안에 이해 가능한 데모 경로”를 만든다.
- 산출물 구조를 정리해 발표/공유/피드백 수집이 가능한 상태로 만든다.
- 남은 고급 항목은 v2 백로그로 분리한다.
  - 실시간성
  - 고급 검색 랭킹
  - 금리/무위험수익률 실데이터
  - 고급 개인화/이력 저장

### Acceptance Criteria
- 저장소 첫 진입 문서만 읽고 로컬 실행 경로를 따라갈 수 있다.
- 발표/시연용 흐름이 단일 종목, 포트폴리오 두 케이스로 준비된다.
- v1과 v2 경계가 명확해져 scope creep 없이 실행 가능한 상태가 된다.

## 5. 파일/영역 기준 영향 범위
- 제품/구조 문서: `엔진내부구조.md`, `추천판정기준.md`, `docs/STEP_1/...`
- 웹 UX: `web/index.html`, `web/app.js`, `web/styles.css`
- 대시보드 서버 계약: `scripts/serve_dashboard.py`
- 엔진/산출물 계약: `scripts/run_data_pipeline.py`
- 회귀 테스트: `tests/test_run_data_pipeline.py`, `tests/test_dashboard_server.py`

예상 복잡도: **HIGH**

이유:
- 코드 변경뿐 아니라 **문서/UX/결과 해석 계약**까지 함께 맞춰야 한다.
- “시장형 제품” 전환은 기능 추가보다 **사용자 흐름과 신뢰도 표현** 정리가 핵심이다.

  - 대응: 결과 구조 우선, 시각 polish는 후순위
- **제품 설명과 엔진 기준 불일치 리스크**
  - 대응: 추천판정기준.md + 엔진내부구조.md + 실행방법 문서를 항상 함께 갱신

## 8. 검증 방법
1. 문서 검증
   - 제품 설명, 구조 문서, 실행 문서의 핵심 용어 일치 여부 확인
2. 기능 검증
   - 단일 종목 분석 1회
   - 포트폴리오 분석 1회
   - 추천안 0건 → 참고안 흐름 1회
3. 자동 검증
   - `python3 -m unittest discover -s tests -v`
4. 시연 검증
   - “처음 보는 사용자 기준 5분 시연” 체크리스트 통과

## 9. 권장 실행 순서

2. Step 2 — 입력 경험 정리
3. Step 3 — 결과 화면 정리
4. Step 4 — 신뢰도/재현성 정리
5. Step 5 — 데모/배포형 패키지 마감

## 10. Planner Handoff Note
이 계획은 **현재 HedgeMate를 새로 갈아엎는 계획이 아니라**,  
이미 있는 엔진/문서/UI를 기반으로 **시장형 MVP로 전환**하는 계획이다.

따라서 구현은 “새 기능 대량 추가”보다 아래에 집중해야 한다.

- 사용자 흐름 단순화
- 추천안/참고안 의미 고정
- 결과 해석 가능성 강화
- 재현 가능한 데모/문서/검증 패키지 확보
