# 헤지메이트 자산 민감도 분석 계획 (2026-03-18)

## 1. 목적
현재 HedgeMate의 다음 단계는 추천 엔진 개편 이전에 **입력 자산의 고유 리스크 민감도(sensitivity)를 정량적으로 분류하는 분석 체계**를 고정하는 것이다.

이 계획은 다음 범위에 한정한다.
- 자산 민감도 분석 프레임워크 정의
- 리스크 taxonomy / 분류 규칙 / 산출물 계약 정의
- 검증 시나리오 및 테스트 기준 정의

이 계획은 다음 범위를 제외한다.
- 추천 점수식/게이트 구현 변경
- 헷지 추천 엔진 개편
- UI/대시보드 결과 화면 개편
- 시장 regime를 추천 점수에 반영하는 로직 구현

---

## 2. 현재 기준선 (repo evidence)
- 문제 인식: `지금 hedgemate의 문제.txt`
- 개선 방향 초안: `0311_hedgemate_hedge_logic_plan.md`
- 지표 정의: `docs/STEP_1/02_데이터표준/02_지표정의서_v1.md`
- 유니버스 메타: `docs/STEP_1/01_개요/03_자산유니버스_메타_v1.csv`
- 현행 지표 계산/산출 계약: `scripts/run_data_pipeline.py`
- 현행 테스트: `tests/test_run_data_pipeline.py`, `tests/test_dashboard_server.py`

이미 존재하는 민감도 관련 입력은 다음과 같다.
- `beta_sp500_1y_krw`
- `downside_beta_sp500_1y_krw`
- `corr_sp500_60d_krw`
- `corr_kospi200_60d_krw`
- `avg_stress_ret_krw`
- `annual_return_1y_krw`
- `sharpe_1y_krw_proxy`

즉, 완전 신규 분석이 아니라 **기존 KRW 기준 feature를 재구성해 자산별 리스크 민감도 라벨로 승격**하는 계획이다.

---

## 3. 실행 계획

## Step 1. 자산 민감도 분석 계약 고정
### 목표
“무엇을 민감도라고 부를지”를 문서 수준에서 먼저 고정한다.

### 작업
- 민감도 분석의 공식 목적을 한 문장으로 고정한다.
  - 예: “입력 자산이 어떤 리스크 요인에 취약한지 정량적으로 추정해, 향후 헷지 논리 선택의 입력으로 사용”
- MVP 리스크 taxonomy를 5~6개로 제한한다.
  - 예: 금리상승 / 경기둔화 / 성장주·고베타 하락 / 인플레이션 / 환율(KRW) / 지정학·에너지
- 단일 자산은 `대표 리스크 1개 + 보조 리스크 1~2개`, 포트폴리오는 `병행 리스크 다건 허용` 원칙을 고정한다.
- “시장분석”은 본 단계에서 **설명 보조용 가설 생성 범위**로 제한하고, 점수 반영은 제외한다.

### Acceptance Criteria
- 민감도 분석 목적, 포함 리스크 taxonomy, 출력 단위가 하나의 문서에 명시된다.
- 포함/제외 범위가 명확해져 추천 엔진 개편 작업과 분리된다.
- “최근 수익률이 좋은 자산 추천”이 아니라 “입력 자산의 고유 리스크 분류”가 공식 목적임이 문서에 반영된다.

---

## Step 2. 기존 feature와 taxonomy 간 매핑 표 정의
### 목표
이미 계산 중인 KRW 기준 지표로 어떤 리스크를 판정할 수 있는지 구조화한다.

### 작업
- 현행 feature(`features_summary`)를 기준으로 리스크별 사용 가능 지표를 매핑한다.
  - 성장/고베타: `beta_sp500_1y_krw`, `downside_beta_sp500_1y_krw`, `corr_sp500_60d_krw`
  - 경기/방어: `avg_stress_ret_krw`, `mdd_1y_krw`, `cvar_95_1y_krw`
  - 한국시장/글로벌시장 민감: `corr_kospi200_60d_krw`, `corr_sp500_60d_krw`
  - 수익 훼손 특성 보조: `annual_return_1y_krw`, `sharpe_1y_krw_proxy`
- 각 taxonomy에 대해
  1. 필수 지표
  2. 보조 지표
  3. 현재 repo에 없는 지표(추가 수집/계산 필요)
  를 표로 정리한다.
- 현재 유니버스 메타(`asset_class`, `group_tag`, `region`, `currency`)가 민감도 추정에 어디까지 보조 신호로 허용되는지 경계를 정한다.

### Acceptance Criteria
- 각 리스크 taxonomy마다 “판정 근거 지표”가 최소 2개 이상 정의된다.
- 현재 지표로 가능한 것과 불가능한 것이 구분된다.
- 수작업 메타데이터는 보조 신호일 뿐, 최종 판정의 유일 근거가 아님이 명시된다.

---

## Step 3. 자산 민감도 판정 규칙과 confidence 규칙 설계
### 목표
자산별로 대표/보조 리스크를 재현 가능하게 붙일 수 있는 판정 규칙을 만든다.

### 작업
- 리스크별 점수화 규칙을 정의한다.
  - 예: z-score / percentile / threshold 기반
- `대표 리스크 1개` 선정 규칙을 정의한다.
  - 최고 점수 1개 선택
  - 동점 처리
  - 신뢰도 부족 시 `대표 리스크 없음`
- `보조 리스크` 선정 규칙을 정의한다.
  - 대표 리스크와 충분히 근접한 score만 채택
- confidence 규칙을 정의한다.
  - 데이터 충분성
  - 지표 일관성
  - 지표 간 충돌 여부
- 자산군별 예외 규칙을 정한다.
  - 금/채권/원자재/방어섹터/암호화폐처럼 해석이 쉬운 자산군도 **메타데이터로 자동 확정하지 않고**, 지표와 상충 시 confidence를 낮춘다.

### Acceptance Criteria
- 동일 입력 데이터에서 동일 자산이 반복 실행 시 동일 리스크 라벨을 받는다.
- 데이터 부족/지표 충돌 시 confidence 하락 또는 미분류 처리가 가능하다.
- 대표/보조 리스크 선정 규칙이 pass/fail 형태로 검토 가능하다.

---

## Step 4. 산출물 계약과 검증셋 정의
### 목표
민감도 분석 결과가 이후 엔진/문서/테스트에서 재사용 가능한 형식으로 고정된다.

### 작업
- 신규 산출물 또는 기존 `features_summary` 확장 방식 중 하나를 선택해 결과 계약을 문서화한다.
  - 후보 예시: `asset_risk_sensitivity_{run_id}.csv`
- 필수 컬럼을 정의한다.
  - `ticker`
  - `primary_risk`
  - `secondary_risks`
  - `risk_scores`
  - `confidence`
  - `evidence_metrics`
- 대표 검증셋을 만든다.
  - 미국 성장주 1종
  - 한국 대형주 1종
  - 금 ETF 1종
  - 국채 ETF 1종
  - 원자재/에너지 1종
  - 암호화폐 1종
- 검증 기준을 정한다.
  - 라벨이 전혀 상식과 반대로 나오는지
  - confidence가 과도하게 높거나 낮지 않은지
  - 미분류 비율이 허용 범위 내인지

### Acceptance Criteria
- 민감도 산출물의 컬럼 계약이 명시된다.
- 최소 6개 대표 자산 검증셋과 기대 라벨/허용 오차 원칙이 정의된다.
- 후속 구현자가 테스트 케이스를 바로 만들 수 있는 수준으로 결과 계약이 구체화된다.

---

## Step 5. 구현 handoff 패키지 정리
### 목표
이 분석 계획이 바로 후속 planner/architect/executor 작업으로 이어질 수 있게 한다.

### 작업
- 후속 구현 작업을 3개 lane으로 분리한다.
  1. 문서 lane: taxonomy/판정 규칙 명세
  2. 데이터 lane: feature 계산 gap 보완 여부 검토
  3. 검증 lane: 회귀 테스트/검증셋 설계
- 후속 구현의 비범위를 명시한다.
  - 추천 점수식 변경 금지
  - UI 노출 방식 변경 금지
  - 시장 예측 엔진 추가 금지
- architect 검토 포인트를 따로 적는다.
  - 기존 `features_summary` 확장 vs 신규 파일 분리
  - 지표 추가가 필요한 taxonomy의 데이터 가용성
- planner 후속 입력 문장을 남긴다.
  - “자산 민감도 분석 규칙 명세를 구현 가능한 작업 단위로 분해”

### Acceptance Criteria
- 후속 실행자가 바로 착수 가능한 lane별 handoff 메모가 존재한다.
- 구현 범위와 비범위가 명확해 scope creep를 막을 수 있다.
- planner/architect가 재탐색 없이 후속 계획 또는 코드 분석으로 넘어갈 수 있다.

## 6. 주요 리스크
- **범위 팽창 리스크**: 시장해석/추천엔진 개편까지 같이 끌려갈 수 있음
  - 대응: 본 계획은 민감도 분석 정의까지만 제한
- **taxonomy 과세분화 리스크**: 리스크 종류를 너무 많이 나누면 판정 재현성이 떨어짐
  - 대응: MVP는 5~6개로 제한
- **메타데이터 과의존 리스크**: `asset_class`, `group_tag`만으로 자산 성격을 고정할 위험
  - 대응: 메타데이터는 보조 신호로만 허용
- **설명 가능성 부족 리스크**: score는 있는데 왜 그런지 설명이 약할 수 있음
  - 대응: `evidence_metrics` 컬럼을 결과 계약에 포함

---

## 7. 검증 방법
1. 문서 검증
   - taxonomy / 판정 규칙 / 결과 계약이 상호 모순 없는지 점검
2. 데이터 검증
   - 현재 `features_summary` 컬럼만으로 각 taxonomy를 얼마나 커버 가능한지 확인
3. 대표 자산 sanity check
   - 성장주 / 금 / 채권 / 에너지 / 암호화폐 등 대표 자산 라벨이 상식적으로 해석 가능한지 검토
4. 후속 구현 적합성 검증
   - 구현자가 추가 질의 없이 테스트 케이스를 설계할 수 있는 수준인지 확인

## 9. Planner Handoff Note
이 계획은 **추천을 어떻게 할지**가 아니라,
그 전에 반드시 필요한 **“입력 자산이 무엇에 민감한가”를 정량적으로 정의하는 단계**다.

후속 실행은 아래 순서를 권장한다.
- planner: 구현 가능한 세부 작업 계획 분해
- architect: 기존 feature 계약으로 충분한지 코드/데이터 구조 검토
- executor: 문서/산출물/테스트 계약 구현
