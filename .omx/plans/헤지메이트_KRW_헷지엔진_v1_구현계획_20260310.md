# 헤지메이트 KRW 헷지엔진 v1 구현계획 (2026-03-10)

## 1. Requirements Summary
- 현재 저장소는 Step1~Step5 데이터 파이프라인 MVP를 완료했고, 단일 스크립트 `scripts/run_data_pipeline.py`가 데이터 수집, 지표 계산, HES 랭킹, 포트폴리오 비교, 리포트 생성을 모두 수행한다 (`docs/STEP_1/03_운영/03_진행현황.md:14-45`, `scripts/run_data_pipeline.py:567-610`, `scripts/run_data_pipeline.py:802-870`, `scripts/run_data_pipeline.py:873-940`, `scripts/run_data_pipeline.py:944-1362`).

## 2. Planning Assumptions
- v1에서는 **거래일 정렬 정책을 새로 확정하지 않고**, 현재 코드가 이미 사용 중인 **교집합 기반 정렬**을 유지한다. 이는 포트폴리오 수익률 계산과 beta/corr 계산이 모두 교집합 날짜를 사용하기 때문이다 (`docs/STEP_1/03_운영/03_진행현황.md:42-45`, `scripts/run_data_pipeline.py:466-492`, `scripts/run_data_pipeline.py:745-776`).
- v1의 Sharpe는 요구사항 문서대로 **무위험수익률 0% proxy**로 시작한다 (`docs/STEP_1/03_운영/06_현업형_헷지규칙_v1_요구사항_20260310.md:42-49`).
- v1에서는 **새 의존성 추가 없이** 표준 라이브러리(`argparse`, `unittest`)와 기존 Yahoo 수집 경로를 재사용한다 (`scripts/run_data_pipeline.py:146-203`).
- 기존 CSV 산출물은 깨지지 않도록 유지하되, KRW 기준 컬럼과 신규 단일종목 산출물을 **추가**하는 방향으로 간다 (`docs/STEP_1/03_운영/06_현업형_헷지규칙_v1_요구사항_20260310.md:186-223`).

## 3. Scope
### In Scope
- KRW 환산용 FX 수집 및 KRW 수익률 파이프라인 추가
- `annual_return_1y_krw`, `sharpe_1y_krw_proxy` 포함 KRW 지표 확장
- 후보군을 채권/금/원자재/방어섹터/암호화폐까지 반영
- 포트폴리오 입력 모드 유지 + 단일 종목 질의 모드 추가
- 1~4개 자산 조합 추천과 복합 점수식 도입
- 산출 CSV/문서/실행방법/데이터명세/지표정의서 업데이트
- 회귀 테스트 및 검증 절차 추가

### Out of Scope
- 옵션/선물/스왑 기반 직접 헷지 구현
- 실시간 API/챗 서비스 배포
- 동적 FX overlay 고도화
- KRW 무위험수익률 실데이터 연결 (v2)
(`docs/STEP_1/03_운영/06_현업형_헷지규칙_v1_요구사항_20260310.md:227-235`)

## 5. Implementation Steps

### Phase 0 — 인터페이스 고정 및 작업 발판 정리
1. `scripts/run_data_pipeline.py`에 `argparse` 기반 CLI를 추가해 기존 기본 실행은 유지하고, 신규 옵션 `--single-asset`, `--hedge-budgets`, `--max-combo-size`, `--candidate-mode`를 수용한다. 현재 스크립트는 파라미터 없이 `main()`만 실행하므로(`scripts/run_data_pipeline.py:567-610`, `scripts/run_data_pipeline.py` tail), 질의 모드를 추가하려면 CLI 진입점이 먼저 필요하다.
2. `tests/test_run_data_pipeline.py`를 신규 추가해 순수 함수 중심 회귀 테스트 기반을 만든다. 신규 의존성 없이 표준 라이브러리 `unittest` 사용을 기본으로 한다.
3. 문서 상 임시 정책을 명시한다: v1은 거래일 정렬을 교집합 기반으로 유지하고, 무위험수익률은 0% proxy를 사용한다 (`docs/STEP_1/03_운영/03_진행현황.md:42-45`, `docs/STEP_1/03_운영/06_현업형_헷지규칙_v1_요구사항_20260310.md:42-49`).

### Phase 1 — KRW 환산 파이프라인 도입
1. 기존 Yahoo 차트 수집 함수 `fetch_yahoo_chart()`를 재사용해 `KRW=X` 환율 시계열을 가져오는 FX 수집 경로를 추가한다 (`scripts/run_data_pipeline.py:146-203`).
2. `main()`의 수집 단계에서 자산 시계열을 적재한 뒤, USD 자산은 `adj_close * usdkrw_rate`로 KRW 가격 시계열을 생성하고, KRW 자산은 `fx_rate=1.0`으로 처리한다 (`scripts/run_data_pipeline.py:595-610`, `docs/STEP_1/03_운영/06_현업형_헷지규칙_v1_요구사항_20260310.md:31-34`).
3. 재현성을 위해 신규 산출물 `outputs/raw/raw_fx_daily_YYYYMMDD.csv` 또는 동등한 FX raw 산출물을 추가한다. 문서와 코드가 모두 이 산출물을 참조하도록 정리한다.
4. FX 결측/불일치에 대한 처리 규칙을 코드와 문서에 명시한다.
   - 우선순위: exact date match → 최근 과거 영업일 carry-forward(허용 범위 제한) → 해당 일자 metric 제외
   - 이유: 미국/한국/암호화폐 거래일 차이로 exact intersection만 강제하면 FX 결측이 잦아질 수 있음.

### Phase 2 — KRW 지표 및 Sharpe 확장
1. 현재 자산 지표 계산 블록을 KRW 시계열 기준으로 확장한다. 현재 `feature_rows`는 `vol_annual`, `mdd_1y`, `var_95_1y`, `cvar_95_1y`, `beta`, `corr`, `avg_stress_ret`, `adv_60`만 채운다 (`scripts/run_data_pipeline.py:719-817`). 여기에 `annual_return_1y_krw`, `sharpe_1y_krw_proxy`, KRW 기반 risk metric 컬럼을 추가한다.
2. `portfolio_metrics_from_returns()`를 확장해 `annual_return_krw`, `sharpe_krw_proxy`, `stress_avg_ret_krw`, 필요 시 `beta_sp500_krw` 또는 `corr_sp500_krw`를 반환하게 만든다. 현재는 `vol_annual`, `mdd`, `cvar_95`만 계산한다 (`scripts/run_data_pipeline.py:495-517`).
3. 기존 출력 CSV는 호환성을 위해 유지하되, 신규 KRW 컬럼을 병행 추가한다. 저장 스키마 확장은 `features_summary` 작성 구간과 포트폴리오 결과 CSV 작성 구간에서 함께 처리한다 (`scripts/run_data_pipeline.py:851-870`, `scripts/run_data_pipeline.py:1068-1165`).
4. `docs/STEP_1/02_데이터표준/01_데이터명세_v1.md`와 `docs/STEP_1/02_데이터표준/02_지표정의서_v1.md`를 업데이트해 KRW 기준 컬럼 정의, Sharpe proxy 정의, FX raw 산출물을 반영한다 (`docs/STEP_1/02_데이터표준/01_데이터명세_v1.md:31-64`, `docs/STEP_1/02_데이터표준/02_지표정의서_v1.md:11-101`).

### Phase 3 — 후보군/랭킹/통과 규칙 재정의
1. 후보군을 현재 “전 유니버스 HES Top10” 방식에서 요구사항 기반 헷지 후보군으로 분리한다. 후보군 원천은 메타 CSV의 헷지 후보 플래그와 요구사항 문서의 티커 목록을 합쳐 관리한다 (`docs/STEP_1/01_개요/03_자산유니버스_메타_v1.csv:50-71`, `docs/STEP_1/03_운영/06_현업형_헷지규칙_v1_요구사항_20260310.md:55-76`).
2. `docs/STEP_1/01_개요/03_자산유니버스_메타_v1.csv`에서 `USO`, `XLE`의 후보 여부를 요구사항과 맞게 조정하거나, 별도 `hedge_v1_candidate` 컬럼을 추가해 후보군을 명시적으로 관리한다.
3. 현재 HES 계산 블록은 corr/cvar/stress/liquidity만 반영한다 (`scripts/run_data_pipeline.py:873-920`). 이를 통과규칙 + 최종점수 2단계 구조로 바꾼다.
   - Gate: `CVaR 개선 > 0`, `MDD 개선 >= 0`, `Stress 개선 >= 0`, `beta/corr 감소`, `유동성 통과`, `DQ FAIL 제외`
   - Score: `35/20/20/10/10/5`
4. Sharpe는 gate가 아니라 score component로만 사용한다. 추천 설명용 구성요소 컬럼도 함께 저장한다.
5. 후보 사전 압축 로직을 추가한다.
   - 자산군별 예비점수 계산
   - 자산군별 Top-K 선별
   - 축소 후보군만 조합 탐색

### Phase 4 — 포트폴리오 모드 유지 + 단일 종목/1~4개 조합 추천 추가
1. 기존 포트폴리오 입력 모드는 그대로 유지한다 (`scripts/run_data_pipeline.py:418-463`, `scripts/run_data_pipeline.py:944-1165`, `docs/STEP_1/02_데이터표준/01_데이터명세_v1.md:115-130`).
2. 신규 단일 종목 질의 모드를 추가한다.
   - 입력: `--single-asset TSLA`
   - 기준 포트폴리오: `TSLA 100%`
   - 헷지 예산: `10/20/30`
   - 자기 자신 중복 추천 금지
   - 헷지 자산 개별 cap: 기본 20%
3. 현재 조합 탐색은 `top_candidate_tickers[:5]`의 2개 조합만 계산한다 (`scripts/run_data_pipeline.py:1018-1066`). 이를 1~4개 조합, 다중 예산 시나리오로 확장한다.
4. 조합 다양성 제약을 적용한다 (`docs/STEP_1/03_운영/06_현업형_헷지규칙_v1_요구사항_20260310.md:108-124`).
   - 2개 이상 조합은 최소 2개 자산군 포함
   - 동일 자산군 최대 2개
   - 암호화폐 조합당 최대 1개
5. 신규 산출물을 추가한다.
   - `outputs/reports/single_asset_hedge_1to1_YYYYMMDD.csv`
   - `outputs/reports/single_asset_hedge_multi_YYYYMMDD.csv`
   - `outputs/reports/single_asset_compare_YYYYMMDD.csv`
6. 기존 `portfolio_compare`는 계속 생성하되, “best by CVaR 단독”에서 “gate 통과 후 복합점수 최고”로 선택 기준을 바꾼다 (`scripts/run_data_pipeline.py:1012-1014`, `scripts/run_data_pipeline.py:1062-1064`, `scripts/run_data_pipeline.py:1113-1165`).

## 7. Risks and Mitigations
- **FX 날짜 불일치 리스크**: 미국/한국/암호화폐와 USD/KRW 날짜가 완벽히 안 맞을 수 있다. → exact match + 제한적 carry-forward 규칙을 문서화하고 테스트한다.
- **조합 폭발 리스크**: 1~4개 조합은 전수탐색 시 경우의 수가 커진다. → 자산군별 Top-K 선별 후 축소 후보군만 탐색한다 (`docs/STEP_1/03_운영/06_현업형_헷지규칙_v1_요구사항_20260310.md:114-124`).
- **암호화폐가 “헷지”보다 “위험자산”으로 작동할 리스크**: → gate에서 CVaR/MDD/Stress 개선을 필수화하고, 암호화폐는 조합당 최대 1개로 제한한다 (`docs/STEP_1/03_운영/06_현업형_헷지규칙_v1_요구사항_20260310.md:108-112`, `docs/STEP_1/03_운영/06_현업형_헷지규칙_v1_요구사항_20260310.md:155-166`).
- **기존 산출물 호환성 리스크**: → 기존 컬럼은 유지하고 KRW 컬럼을 추가한 뒤, 보고서/랭킹의 canonical metric만 KRW 기준으로 전환한다.
- **네트워크 의존 리스크**: → 실행 검증은 캐시 raw 재사용 경로와 FX raw 재사용 경로를 함께 지원해 재실행 안정성을 확보한다 (`scripts/run_data_pipeline.py:590-595`, `scripts/run_data_pipeline.py:1187`).
